## Core Task

Your task is to act as the custodian of the categorized code rules markdown file. Based on the provided context of a successful local performance optimization, you must propose updates to this central knowledge base by generating a diff. Your response should consist of your thought process followed by final diffs.

Your generated diff can be a combination of the following actions:

1. **ADD**: Introduce a new, universally applicable rule under the correct category.
2. **REPLACE**: Overwrite an existing rule to refine it.
3. **DELETE**: Remove an incorrect, outdated, or redundant rule.

## Core Maintenance Principles (Must Adhere)

1. Prefer Refinement over Addition: Your primary goal is to maintain the conciseness and authority of the knowledge base. If a related concept already exists, you must prioritize refining the existing rule via REPLACE instead of adding a new one via ADD. Only use ADD when the optimization principle is genuinely new and has no conceptual overlap.

2. Eliminate Redundancy and Contradiction: Before proposing any change, you must ensure it does not duplicate or contradict existing rules. If a new finding conflicts with an existing rule, your task is to resolve the conflict by modifying the Apply condition or replacing the old rule with a more precise one.

## Thinking Process

Before generating any diff, you can follow these thinking steps (internally or externally) to generate thinking content step by step:

1. Search Phase: First, thoroughly search the existing knowledge base for any rules related to the current performance optimization. Look for conceptual similarities, not just keyword matches.

2. Decision Phase: Based on your search results, make a decision:

  - Case A: Fully Covered? If the optimization principle is perfectly covered by an existing rule -> Output nothing.

  - Case B: Conceptually Related? If a related rule exists but can be improved, generalized, or made more precise -> Prepare a REPLACE operation.

  - Case C: Genuinely Novel? If the principle is entirely new and has no conceptual overlap with any existing rules -> Prepare an ADD operation.

3. Formulation Phase: When preparing an ADD or REPLACE operation, formulate the rule's core principle to be concrete and actionable. Avoid high-level platitudes. The principle should describe a specific technique (e.g., "Use sentinels to eliminate boundary checks in loops") rather than a vague goal (e.g., "Optimize loops"). However, ensure the rule remains general enough to apply across different problems, avoiding task-specific details like variable names.

4. Action Phase: Generate the corresponding diff based on your decision.
